## 2. Introduction and Objectives

### 2.1 Purpose

This plan defines the verification strategy for the etcd bootstrap member recovery fix in [ARO-30375](https://redhat.atlassian.net/browse/ARO-30375). A late-starting etcd member with an empty data directory can remove its bootstrap identity, fail to add a replacement, and then restart as if the cluster were new. That recreates an identity etcd has already removed, which can leave the hosted control-plane etcd pod in a crash loop and block kube-apiserver startup.

[PR #10118](https://github.com/openshift/hypershift/pull/10118) makes reset-member and recovery idempotent. It preserves the observed `existing` cluster state, repairs interrupted remove/add operations, refuses to start etcd while a membership change is unconfirmed and the cluster cannot be listed, and waits for every member endpoint to become healthy before reporting success. [PR #10035](https://github.com/openshift/hypershift/pull/10035) is a merged prerequisite that classifies an unstarted member with no client URL as unhealthy instead of aborting recovery.

[OCPBUGS-140635](https://redhat.atlassian.net/browse/OCPBUGS-140635) provides the release-facing description of the same failure. It records that the defect is intermittent and depends on member-startup timing plus a transient DNS, connectivity, or unhealthy-cluster failure during member replacement. The issue also distinguishes PR #10035's empty-client-URL recovery fix from the remaining reset-member bootstrap-state and recovery-completion work in PR #10118.

**Review follow-up (2026-11-17, pushed 2026-11-19 as commit `d50545fddb`).** Review of PR #10118 reported a startup deadlock in the first revision: after the script observed a functional cluster and wrote `existing`, any later member-list failure made it exit nonzero. With quorum lost and the member still registered, etcd could never start, although starting it as `existing` would have restored quorum. The base script did not have this problem, but it also restarted a removed identity as `new`. The script now lists members once and decides from that result, and it keeps a separate `repair` marker that is present only while a membership change is unconfirmed. It refuses to start etcd only while that marker is present. The shard script is now derived from the default asset instead of being a second copy, and the recovery flow can be driven in tests without clients or real polling delays. TC-009, TC-010 and TC-011 were added, and TC-001, TC-002, TC-003, TC-006 and TC-008 were revised to match. All three open review threads on the follow-up (fake-etcdctl script test, recovery flow test, derive-the-shard-script) are resolved as of the push.

### 2.2 Objectives

1. Verify that an interrupted remove/add operation cannot recreate a permanently removed etcd identity.
2. Verify that reset-member refuses to start etcd while a membership change is unconfirmed and the cluster cannot be listed.
3. Verify that absent members are added by peer URL and that exact-name matching prevents accidental identity reuse.
4. Verify that recovery classifies an unstarted member with no client URL as unhealthy without deleting a non-restarting pod.
5. Verify that recovery preserves quorum when a failing pod differs from the unhealthy member.
6. Verify that recovery waits until every member endpoint is healthy before reporting success.
7. Verify that the shared and sharded reset-member scripts do not drift.
8. Verify that the end-to-end etcd chaos suite still recovers from member loss and preserves data.
9. Verify that an observed cluster with no pending membership change starts etcd when members cannot be listed, so a member that is still registered can help restore quorum.
10. Verify that the script decides from a single member list and that its name and peer-URL matching works on real etcdctl output.
11. Verify on a real etcd cluster that, with quorum lost and the member still registered, the script lets etcd start and quorum return, and that the original revision did not.

## 5. Test Cases

### 5.1 TC-001: Interrupted Remove/Add Does Not Recreate a Removed Identity

- **CI Tier:** unit
- **Target File Path:** `control-plane-operator/controllers/hostedcontrolplane/v2/etcd/resetmember_script_test.go`
- **Coverage Status:** covered
- **Implementation Status:** implemented in PR #10118 as `TestResetMemberScriptBehavior`, which executes the script with a fake `etcdctl`
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; sharded variant on `main`, `release-5.0`, and `release-4.23`
- **Traceability:** ARO-30375 fix criterion; AROSLSRE-2328 root cause

**Objective:** Verify that reset-member retries preserve `existing` state and repair membership without restarting a removed identity as a new cluster member.

**Preconditions:**
- Rendered shared and sharded reset-member scripts, executed by the test.
- Empty etcd data directory; `/var/lib/data/member/snap/db` must not exist. Both reset-member scripts guard membership repair with `[[ ! -f /var/lib/data/member/snap/db ]]`, so a zero-byte file at that path is treated as existing data and skips the remove/add path.
- Fake `etcdctl` that lists members, permits `member remove`, then fails `member add`.

**Primary method (automated):**
- Run `TestResetMemberScriptBehavior`. It runs each scenario against the default script and the sharded script, and checks that every call targets the right client service and every added member uses the right discovery service.
- Cases include remove succeeds then add fails then add succeeds on retry, remove commits but its response is lost, and add commits but its response is lost.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run reset-member with a mocked `member remove` that succeeds and a mocked `member add` that fails | Script exits nonzero, the `state` marker is `existing`, the `repair` marker is still present, and the mock records a `member remove` followed by a failed `member add` |
| 2 | Retry with mocked successful `member add` | Replacement member is added by peer URL and the `repair` marker is removed |
| 3 | Inspect etcd startup state | Removed identity is not restarted as `new` |

### 5.2 TC-002: Unconfirmed Membership Change Fails Closed When Members Cannot Be Listed

- **Coverage Status:** covered
- **Implementation Status:** implemented in PR #10118 as `TestResetMemberScriptBehavior`
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; sharded variant on `main`, `release-5.0`, and `release-4.23`

**Objective:** Verify that reset-member refuses to start etcd while a membership change is unconfirmed and the cluster cannot be listed, and that it completes the change once the cluster can be listed again.

The scenarios reach this state by failing `member add` after a successful `member remove`, by failing `member add` for a member that was never registered, and by failing `member remove` with an unknown outcome.

**Primary method (automated):**
- Run `TestResetMemberScriptBehavior`. The sequence from review is covered: removal succeeds, addition fails, the next attempt cannot list members and must fail with `existing` preserved, connectivity returns, the missing member is added once, and one more retry reuses that unnamed member without a second add.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run reset-member with the `repair` marker present and `member list` failing | Exit is nonzero |
| 2 | Read logs | Contains `refusing to start etcd` |
| 3 | Read markers | `state` remains `existing` and `repair` remains present |
| 4 | Restore `member list` and run again | The member is added by peer URL and the `repair` marker is removed |

### 5.6 TC-006: Recovery Waits for Every Healthy Endpoint

- **CI Tier:** unit
- **Target File Path:** `etcd-recovery/etcdrecovery_test.go`
- **Coverage Status:** covered
- **Implementation Status:** implemented in PR #10118
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`

### 5.7 TC-007: Deterministic E2E Interrupted Membership Recovery

- **CI Tier:** e2e-serial
- **Target File Path:** `test/e2e/v2/tests/etcd_chaos_test.go`
- **Coverage Status:** partial
- **Implementation Status:** existing suite is automated; exact interruption path is proposed
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; shared path only on 4.20 through 4.22, both variants on 5.0, 4.23 and `main`
- **Traceability:** ARO-30375 root-cause and fix criteria

**Objective:** Reproduce the interrupted remove/add path and verify hosted control-plane recovery.

**Preconditions:**
- Dedicated healthy HCP with three managed etcd members.
- Authorized access to the management cluster and HCP namespace.
- Fault injection or an equivalent deterministic mechanism for a transient DNS, connectivity, or unhealthy-cluster failure during `MemberAdd`.
- Baseline snapshot of etcd pods, PVCs, member list, and HostedCluster conditions.

**Primary method (automated):**
- Extend the existing `etcd-chaos` suite with a deterministic interruption scenario.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Remove one etcd member and delete its pod and PVC | Member has empty data on restart |
| 2 | Arm the fault before reset-member reaches `MemberAdd`, scoped to that operation only | Surviving members keep quorum throughout (the quorum-loss variant is TC-009) |
| 3 | Observe the interrupted repair | Init-container exits nonzero after the `existing` marker is persisted and the `MemberAdd` call fails |
| 4 | Disarm the fault and let reset-member retry | Retry runs in the same pod (same Pod UID); no `member remove`/`member add` pair is re-run from a fresh identity and the removed identity is not recreated |
| 5 | Wait for convergence | Member is added by peer URL and etcd StatefulSet becomes ready |
| 6 | Verify hosted control plane | kube-apiserver starts, etcd is available, rollout completes |
| 7 | Verify data durability | Marker object written before disruption remains readable |

Final readiness alone does not demonstrate that the interruption path was exercised, because member listing happens before the add and the recovery Job has a separate `MemberAdd` path. The expected results in steps 3 and 4 are therefore assertions about the fault and the retry, not just about the converged state.

The existing five `etcd-chaos` specs cover adjacent member loss, kill, corruption, and removal scenarios, but not this exact interrupted remove/add retry sequence. This scenario keeps quorum on purpose. Losing quorum between a failed attempt and its retry is covered at script level by TC-009 and TC-002, because holding a member down in the e2e suite is destructive and not deterministic. The existing five specs were re-run green on the review follow-up build on 2026-11-18 (see section 3.2.1); the deterministic interruption spec itself remains to be implemented.

### 5.9 TC-009: Observed Cluster Without a Pending Membership Change Starts etcd When Members Cannot Be Listed

- **CI Tier:** unit
- **Target File Path:** `control-plane-operator/controllers/hostedcontrolplane/v2/etcd/resetmember_script_test.go`
- **Coverage Status:** covered
- **Implementation Status:** implemented in PR #10118 as `TestResetMemberScriptBehavior`
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; sharded variant on `main`, `release-5.0`, and `release-4.23`
- **Traceability:** review of PR #10118, startup deadlock after a transient member-list failure with quorum lost

**Objective:** Verify that when a functional cluster was observed earlier in this Pod and no membership change is pending, the script exits successfully when members cannot be listed, so etcd starts as `existing` and a member that is still registered can help restore quorum. Verify that a list failure right after a successful list cannot wedge the init container.

**Preconditions:**
- Empty etcd data directory and a member that is still registered.
- Case A: the `state` marker is `existing`, the `repair` marker is absent, and `member list` fails.
- Case B: the first `member list` succeeds and a second one would fail.

**Primary method (automated):**
- Run `TestResetMemberScriptBehavior`. In case A the script exits 0, logs that the cluster is likely not up yet, leaves `state` as `existing`, and makes no `member remove` or `member add` call. In case B the script completes because it lists members once.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run reset-member with `existing` in `state`, no `repair` marker, and `member list` failing | Exit is 0 and etcd would start with `ETCD_INITIAL_CLUSTER_STATE=existing` |
| 2 | Repeat with the `repair` marker present | Exit is nonzero (TC-002) |
| 3 | Run with a mock whose second `member list` fails | The script never makes a second call and completes |

Known limit: if `member remove` fails with an unknown outcome and quorum is then lost, the `repair` marker is present, so the script refuses until members can be listed again, even if the removal never committed. See Section 6.

### 5.11 TC-011: Real etcd Does Not Deadlock When Quorum Is Lost and the Member Is Still Registered

- **CI Tier:** manual (live)
- **Target File Path:** none (throwaway three-member etcd in a scratch namespace)
- **Coverage Status:** not covered
- **Implementation Status:** manual procedure, run once on 2026-11-17 against etcd 3.6.13
- **OCP Version Applicability:** every release that carries the script; repeat when the etcd version changes
- **Traceability:** objective 11; review of PR #10118, startup deadlock

**Objective:** Verify on a real etcd that a member with an empty data directory, whose cluster-state marker says `existing`, starts etcd and restores quorum when the cluster has lost quorum and the member is still registered.

**Preconditions:**
- A StatefulSet of three etcd members built from the production etcd container settings, with the script under test as the `reset-member` init container and the default service names, so the script runs unmodified.
- A harness init container that can hold a member back and can seed `existing` into the cluster-state marker, which stands for an earlier attempt in the same Pod that observed the cluster.

**Primary method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Start with etcd-2 held back | etcd-0 and etcd-1 form a quorum of two out of three; etcd-2 is registered without a client URL |
| 2 | Hold etcd-1 down and delete its Pod | `etcdctl member list` fails on etcd-0, which confirms quorum is lost |
| 3 | Seed `existing` for etcd-2 and release it | With the base script and with the fixed script, `reset-member` exits 0, etcd-2 starts and joins etcd-0. With the first revision of PR #10118, `reset-member` exits 1 on every retry and etcd never starts |
| 4 | Run `etcdctl member list` and `endpoint health --cluster` through etcd-0 | After step 3 with the fixed script, all three members are listed with etcd-2 started, and etcd-0 and etcd-2 commit proposals; etcd-1 is unhealthy only because it is held down |
| 5 | Repeat with quorum available and nothing seeded | The fixed script removes and re-adds etcd-2, and all three members are started and healthy |

## 6. Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| The cluster-state marker is an `emptyDir`, so it does not survive pod replacement | High | Medium | Document the limitation and require a separate design before extending coverage to cross-pod interruption |
| Existing e2e tests do not reproduce the exact interrupted remove/add race | High | High | TC-007 adds deterministic interruption rather than relying on timing |
| `member remove` or `member add` fails with an unknown outcome and quorum is then lost, so the `repair` marker makes the script refuse even though the removal may never have committed | Low | Medium | Accepted. The script cannot tell removed from not removed without a quorum read. `etcdctl member list --consistency=s` could, but it exists only in etcd 3.6 and not in 3.5, so it is not used. Another member must return to restore quorum, and the retry then completes the change. Covered by TC-002 |
| PR #10129 changes recovery debounce and may conflict textually | Medium | Medium | Rebase and rerun after adjacent work merges |
| The requested backport list omits `release-4.23`, which contains the sharded script | Medium | Medium | Confirm with the bug owner whether `release-4.23` needs the change |
| Backports omit required sharded changes or apply them to branches without sharded etcd | Medium | High | Apply only shared changes on 4.20 through 4.22; apply shared and sharded changes on 5.0 |
| Backport prerequisite ordering is missed | Medium | High | Apply PR #10035 before PR #10118 on `release-5.0`, `release-4.22`, `release-4.21`, and `release-4.20` |
| Code applicability is mistaken for independent reproduction on every release | Medium | Medium | Record release-specific validation for each backport; do not infer a pass on one branch from another |
