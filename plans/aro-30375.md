## 2. Introduction and Objectives

### 2.1 Purpose

This plan defines the verification strategy for the etcd bootstrap member recovery fix in [ARO-30375](https://redhat.atlassian.net/browse/ARO-30375). A late-starting etcd member with an empty data directory can remove its bootstrap identity, fail to add a replacement, and then restart as if the cluster were new. That recreates an identity etcd has already removed, which can leave the hosted control-plane etcd pod in a crash loop and block kube-apiserver startup.

[PR #10118](https://github.com/openshift/hypershift/pull/10118) makes reset-member and recovery idempotent. It preserves the observed `existing` cluster state, repairs interrupted remove/add operations, refuses bootstrap fallback when an existing cluster cannot be listed, and waits for every member endpoint to become healthy before reporting success. [PR #10035](https://github.com/openshift/hypershift/pull/10035) is a merged prerequisite that classifies an unstarted member with no client URL as unhealthy instead of aborting recovery.

[OCPBUGS-140635](https://redhat.atlassian.net/browse/OCPBUGS-140635) provides the release-facing description of the same failure. It records that the defect is intermittent and depends on member-startup timing plus a transient DNS, connectivity, or unhealthy-cluster failure during member replacement. The issue also distinguishes PR #10035's empty-client-URL recovery fix from the remaining reset-member bootstrap-state and recovery-completion work in PR #10118.

### 2.2 Objectives

1. Verify that an interrupted remove/add operation cannot recreate a permanently removed etcd identity.
2. Verify that reset-member fails closed when an existing cluster cannot be listed.
3. Verify that absent members are added by peer URL and that exact-name matching prevents accidental identity reuse.
4. Verify that recovery classifies an unstarted member with no client URL as unhealthy without deleting a non-restarting pod.
5. Verify that recovery preserves quorum when a failing pod differs from the unhealthy member.
6. Verify that recovery waits until every member endpoint is healthy before reporting success.
7. Verify that the shared and sharded reset-member scripts do not drift.
8. Verify that the end-to-end etcd chaos suite still recovers from member loss and preserves data.

### 2.3 Acceptance Criteria Mapping

| ARO-30375 Acceptance Criterion | Test Cases |
|--------------------------------|------------|
| Root-cause the etcd crashlooping | TC-001, TC-002, TC-003, TC-007 |
| Fix the issue | TC-001 through TC-008 |

### OCPBUGS-140635 Expected Results

| Expected Result | Test Cases |
|-----------------|------------|
| Preserve observed `existing` state across init-container retries in the same Pod | TC-001 |
| Repair interrupted remove/add without duplicating an already registered peer URL | TC-003 |
| Refuse bootstrap fallback after an existing cluster has been observed | TC-002 |
| Report recovery success only after every member endpoint is healthy | TC-006 |
| Preserve existing quorum-safety checks | TC-005 |

### 2.4 Automation-First Principle

The primary verification method is the automated suite delivered with the implementation PRs. Manual execution is a fallback only. Deterministic unit tests are preferred for script branches and recovery decisions; a serial e2e scenario is reserved for the destructive, cluster-scoped interruption path.

## 5. Test Cases

### 5.1 TC-001: Interrupted Remove/Add Does Not Recreate a Removed Identity

- **CI Tier:** unit
- **Target File Path:** `control-plane-operator/controllers/hostedcontrolplane/v2/etcd/shard_test.go`
- **Coverage Status:** not covered
- **Implementation Status:** to be automated
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; sharded variant on `main` and `release-5.0`
- **Traceability:** ARO-30375 fix criterion; AROSLSRE-2328 root cause

**Objective:** Verify that reset-member retries preserve `existing` state and repair membership without restarting a removed identity as a new cluster member.

**Preconditions:**
- Rendered shared reset-member script.
- Empty `/var/lib/data/member/snap/db`.
- Mock `etcdctl` that lists members, permits `member remove`, then fails `member add`.

**Primary method (automated):**
- Add a deterministic shell or extracted-script test to `shard_test.go`.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run reset-member with an `existing` marker and mocked failed `member add` | Script exits nonzero and marker remains `existing` |
| 2 | Retry with mocked successful `member add` | Replacement member is added by peer URL |
| 3 | Inspect etcd startup state | Removed identity is not restarted as `new` |

### 5.4 TC-004: Unstarted Member Is Classified as Unhealthy

- **CI Tier:** unit
- **Target File Path:** `etcd-recovery/etcdrecovery_test.go`
- **Coverage Status:** covered
- **Implementation Status:** implemented in PR #10035 and retained by PR #10118
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`
- **Traceability:** ARO-30375 recovery-stage failure; OCPBUGS-109628

**Objective:** Verify that a member with no client URL is treated as unhealthy rather than malformed, and that a non-restarting pod does not trigger deletion.

**Primary method (automated):**
- Run `TestCheckEtcdStatus` cases:
  - "When a member has not started and its pod is crash looping, it should report a failing pod without erroring"
  - "When a member has not started but no pod has restarted, it should not report the cluster as unhealthy"

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run the focused test | Both cases pass |
| 2 | Inspect zero-restart case | `isUnhealthy()` is false and no PVC deletion is triggered |

- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`
- **Traceability:** PR #10118 wait-before-success behavior

**Objective:** Verify recovery does not report success while any member endpoint is unhealthy.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|

### 5.7 TC-007: Deterministic E2E Interrupted Membership Recovery

- **CI Tier:** e2e-serial
- **Target File Path:** `test/e2e/v2/tests/etcd_chaos_test.go`
- **Coverage Status:** partial
- **Implementation Status:** existing suite is automated; exact interruption path is proposed
- **OCP Version Applicability:** `main`, `release-5.0`, and `release-4.20` through `release-4.22`; shared path only on 4.20 through 4.22, both variants on 5.0 and `main`
- **Traceability:** ARO-30375 root-cause and fix criteria

**Objective:** Reproduce the interrupted remove/add path and verify hosted control-plane recovery.

**Preconditions:**
- Dedicated healthy HCP with three managed etcd members.
- Authorized access to the management cluster and HCP namespace.
- Fault injection or an equivalent deterministic mechanism for a transient DNS, connectivity, or unhealthy-cluster failure during `MemberAdd`.
- Baseline snapshot of etcd pods, PVCs, member list, and HostedCluster conditions.

**Primary method (automated):**
- Extend the existing `etcd-chaos` suite with a deterministic interruption scenario.

**Fallback method (manual):**

| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Remove one etcd member and delete its pod and PVC | Member has empty data on restart |
| 2 | Inject a transient DNS, connectivity, or unhealthy-cluster failure at replacement `MemberAdd` | Repair is interrupted |
| 3 | Retry reset-member with prior `existing` state | Removed identity is not recreated |
| 4 | Wait for convergence | Member is added by peer URL and etcd StatefulSet becomes ready |
| 5 | Verify hosted control plane | kube-apiserver starts, etcd is available, rollout completes |
| 6 | Verify data durability | Marker object written before disruption remains readable |

The existing five `etcd-chaos` specs cover adjacent member loss, kill, corruption, and removal scenarios, but not this exact interrupted remove/add retry sequence.

## 6. Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| The cluster-state marker is an `emptyDir`, so it does not survive pod replacement | High | Medium | Document the limitation and require a separate design before extending coverage to cross-pod interruption |
| Existing e2e tests do not reproduce the exact interrupted remove/add race | High | High | TC-007 adds deterministic interruption rather than relying on timing |
| PR #10129 changes recovery debounce and may conflict textually | Medium | Medium | Rebase and rerun after adjacent work merges |
| Backports omit required sharded changes or apply them to branches without sharded etcd | Medium | High | Apply only shared changes on 4.20 through 4.22; apply shared and sharded changes on 5.0 |
| Backport prerequisite ordering is missed | Medium | High | Apply PR #10035 before PR #10118 on `release-5.0`, `release-4.22`, `release-4.21`, and `release-4.20` |
| Code applicability is mistaken for independent reproduction on every release | Medium | Medium | Record release-specific validation for each backport; do not infer a pass on one branch from another |
