B. Environment finding — konnectivity-server and azure-workload-identity-webhook crash-loops

The hosted control plane never reaches Available in this environment when it is created from scratch by a main-based control-plane operator on a GA OCP payload. Root cause, verified at each link:

#FactEvidence
1The CPO renders --tls-min-version=VersionTLS12 and --cipher-suites=<6 IANA suites> on the konnectivity-server container, and --tls-cipher-suites/--tls-min-version on the azure-workload-identity-webhook, for every CRD-valid TLS profile (nil defaults to Intermediate)cluster/kas-konnectivity-args.txt (live render)
2The GA 4.21.40 payload's proxy-server binary rejects --tls-min-version: error: unknown flag: --tls-min-version; the payload webhook binary rejects -tls-cipher-suitescluster/konnectivity-crashloop.txt · cluster/azure-wi-webhook-crashloop.txt
3All GA payloads checked (4.19.0, 4.20.46, 4.21.40/42/43, 4.22.9/22) ship binaries lacking these flags; no GA version avoids the crash-looppayload digests probed directly during validation
4Upstream CI is green because it uses CI-stream payloads: the passing e2e-v2-azure-self-managed build at the same head renders byte-identical konnectivity-server arguments but a quay-proxy.ci.openshift.org image that accepts themupstream/upstream-comparison.txt
5The flag rendering comes from hypershift main commits 20a145c472, d0083c95e1, 4d4ac2e444, all pre-dating and untouched by PR #10118; the PR's diff touches only etcd codePR diff file list
6The kube-apiserver main container runs and serves 6443 throughout; only the two sidecar containers fail, leaving the pods NotReady and the external API load balancer without backendscluster/kas-container-statuses.txt

Consequences for this verification: the marker-durability specs connected through the framework's port-forward client (see TC-007 deviation 2), and everything else (etcd chaos, recovery Job, convergence) was unaffected. An earlier accepted green run (2026-10-27) reached Available on the same payload because the cluster was initially created by the stock payload CPO, whose render omits the flags; the branch CPO swap afterwards only surged new crash-looping pods while the old Ready pods kept serving the load balancer.

This incompatibility is a main-line issue independent of this PR and is called out here so the next verifier can reproduce the environment without re-deriving the root cause. Suppressing the flags via the HostedCluster TLS profile is not possible: every CRD-valid profile renders them.
