Deviation 1 — hosted control plane is Partial, not Available

The plan's precondition is a "dedicated healthy HCP". The cluster under test has EtcdAvailable=True, InfrastructureReady=True and a serving kube-apiserver, but Available=False because the konnectivity-server and azure-workload-identity-webhook containers in the kube-apiserver pods crash-loop. This is a pre-existing incompatibility between hypershift main TLS-profile propagation (commits 20a145c472, d0083c95e1, 4d4ac2e444, all outside this PR) and GA OCP payload binaries: the rendered flags --tls-min-version=VersionTLS12/--cipher-suites are rejected by the GA 4.x payload's proxy-server and webhook binaries. Upstream CI passes because it consumes CI-stream payloads whose binaries accept the flags; the rendered arguments are otherwise identical. The PR under test changes no TLS or kube-apiserver code. Full root-cause chain with evidence: Appendices.

Everything TC-007 exercises lives in the etcd subsystem (StatefulSet, reset-member, recovery Job) and the kube-apiserver main container, all of which were healthy. The crash-looping containers are data-plane connectivity components with no role in the etcd recovery path.

Deviation 2 — marker specs connected via port-forward

Because all kube-apiserver pods on this from-scratch cluster carry the crash-looping containers, the pods are NotReady and the external API load balancer has no ready backends (TLS handshake timeout). The two marker-durability specs were therefore run with the e2e framework's own GetHostedClusterClientViaPortForward client, which connects to the same kube-apiserver pods on port 6443 through the management cluster API. This is an upstream framework facility intended exactly for environments where external DNS or load balancers are unavailable. The write path still crosses the real kube-apiserver and the real etcd, so durability semantics are unchanged. The local adaptation is 12 lines, was applied only to the test binary (the suite is upstream code, not part of the PR), and is published verbatim: e2e/portforward-adaptation.patch.

Interpretation

The plan marks this test case's coverage partial because the exact deterministic interruption (inject a failure at MemberAdd, then retry) is only proposed as a new suite spec and is not implemented in the PR. The validation therefore composes the deterministic interruption path (TC-001 mock harness: failed add, preserved existing marker, successful retry with peer-URL add) with live end-to-end recovery of every adjacent fault shape on a 3-member cluster rendered by the head CPO. Together these cover the root-cause criteria: no removed identity is ever restarted as a bootstrap member, repairs are idempotent across retries, and quorum plus data survive every injected fault.
