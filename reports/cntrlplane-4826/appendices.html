HostedCluster creation attempts in round 4

The round-3 HostedCluster name could not be recreated: the managed resource group still held an egress load balancer whose health-probe rule referenced a probe that no longer existed, and Azure rejected every update with InvalidResourceReference. Two non-destructive repair attempts also failed. Round 4 therefore used a new HostedCluster and infrastructure name inside the same managed resource group, which keeps the existing workload-identity role assignments and required no Azure deletion. Both failed attempts and the repair logs are archived: cluster/round4-attempts/create-20261029T011739Z · cluster/round4-attempts/create-20261029T012111Z · cluster/round4-attempts/lb-repair-20261029T012423Z .

Reproduction

  1. Build base ee327075b1 and head ee5691233b with podman build -f ./Dockerfile.dev --platform=linux/amd64 and push both images.
  2. Create an Azure self-managed HostedCluster with the CAPI manager overridden with the annotation hypershift.openshift.io/capi-manager-image. Use registry.k8s.io/cluster-api/cluster-api-controller:v1.14.3 for the 1.14 rounds and v1.13.4 for round 5.
  3. Run run-t1.sh baseline with the base image and run-t1.sh patched with the head image. Both scripts snapshot before state, patch release B, sample every 5 s, require an explicit PASS/FAIL and archive operator logs and events.
  4. For the pre-1.14 row, run run-t1.sh patched against the 1.13.4 manager and evaluate its trace with verify-t8.sh, because the stock runner encodes the 1.14 stall signature as its success gate.
