# Verification Report: PR #9988 — kubelet through HAProxy on public HCPs

## Environment

| Property | Value |
|---|---|
| Management cluster | AWS `us-west-2`, `<management-cluster>` |
| HostedCluster | AWS `us-west-1`, `<hosted-cluster>`, 2 workers, `Replace` strategy |
| Release | 5.1.0-0.nightly-2026-10-26-164535 |
| Feature gate | `KubeletHAProxyRouting` enabled |

## Results

| Test Case | Result | Notes |
|---|---|---|
| TC-016 | Partial | The mechanism is verified, the acceptance case is not. Both kubelet kubeconfigs point at `172.20.0.1:6443`, both proxy pods are `Running/Ready` forwarding to the KAS NLB, and pod traffic to `kubernetes.default.svc/healthz` returned `ok` — but on AWS with an NLB. TC-016 asks for an Agent-platform cluster with MetalLB and a deterministic address, which has not run |
| TC-017 | Partial | Private clusters never take the HAProxy branch per `IsPrivateHCP()`; confirmed by unit tests and code path, not by a live private run |
| TC-018 | Partial | GCP is treated as private by the same helper, so it keeps the previous path; unit coverage only |

Robustness runs recorded on the same cluster: HAProxy restart recovered in under
15 seconds with the node staying `Ready`; a blackholed resolver reproduced the
failure mode and the final hold values retained the last known-good address; a
60-second iptables partition moved the node to `Ready=Unknown` after about 56
seconds and back to `Ready=True` about 14 seconds after the rule was removed.
