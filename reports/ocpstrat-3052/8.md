# Verification Report: Ignition System Re-Architecture (OCPSTRAT-3052)

Pre-merge verification of the ignition system re-architecture against the test
plan [`plans/ocpstrat-3052.md`](../../plans/ocpstrat-3052.md). The
implementation is a phased, stacked pull-request series; PR #8 is the
cumulative tip (the series was verified end-to-end as a whole).

## Environment

| Property | Value |
|----------|-------|
| Cluster type | HostedCluster on AWS, `PublicAndPrivate` endpoint access |
| Control-plane / release | OCP 5.1 (pre-release) |
| NodePool upgrade type | Replace |
| NodePool health | autoRepair enabled |
| Activation | `IgnitionPayloadSystem` via `TechPreviewNoUpgrade` |

Verification was performed manually against a live HostedCluster, exercising
both the fresh-deployment path and the gate-OFF → gate-ON adoption/upgrade
path.

## Results

| Test Case | Result | Notes |
|-----------|--------|-------|
| TC-001 — Fresh new-model deployment | **Pass** | Under the gate, the HO deployed the generator, stateless server, and proxy; the CPO carried the tech-preview feature set and stood its legacy ignition-server down (no flapping). The per-NodePool `IgnitionPayload` reported `PayloadGenerated=True`; both nodes booted via the new serving tier (`IgnitionReached=True`). |
| TC-002 — No-roll adoption on gate enablement | **Pass** | Flipping the gate ON on a running legacy cluster adopted the NodePool with **zero roll**: userdata Secret name and infrastructure template unchanged, no Machine recreated (same names and creation timestamps). The NodePool recorded the one-time deployed-generation baseline, and the existing userdata Secret was re-owned by the `IgnitionPayload` CR with its content swapped in place to the new-model signed-token format. The CPO stood down. |
| TC-003 — Scale-up after adoption | **Pass** | A node added after adoption booted from the adopted userdata via the new serving tier and joined (`IgnitionReached=True`); existing nodes were untouched. |
| TC-004 — New NodePool under the gate | **Pass** | A NodePool created while the gate was ON received its own `IgnitionPayload` CR and was born on the generator's canonical userdata naming (no legacy-named userdata Secret); its node booted via the new serving tier and autoRepair health checking was created. |
| TC-005 — Rollout-relevant change rolls | **Pass** | A user MachineConfig change advanced the rollout generation, produced a new canonical userdata Secret, re-pointed the MachineDeployment, and rolled new nodes while old nodes drained. After drain, retention stayed bounded (current + previous) and the superseded payload and its userdata Secret were freed. |
| TC-006 — Management-side-only change (Policy A) | **Pass** | A management-side-only content refresh changed the served payload's config hash **without** advancing the rollout generation; userdata Secret name unchanged and no Machine recreated. A subsequent scale-up node booted with the refreshed content; existing nodes untouched. |
| TC-007 — Teardown / cascade cleanup | **Pass** | Deleting a NodePool cleared the consumer and store-cleanup finalizers and removed the `IgnitionPayload` CR; CR-owned projected ConfigMaps and generator-authored userdata Secrets cascade-deleted; payload-store entries were freed; referenced-in-place core/tuning configs (no owner reference) were left intact; no leaked Secrets remained. |

## Acceptance Criteria

| ID | Criterion | Verdict |
|----|-----------|---------|
| C1 | Generation split from serving; HO owns both under the gate; CPO stands down. | **Pass** (TC-001, TC-004) |
| C2 | Booting node fetches payload from the new serving tier with a signed bearer token. | **Pass** (TC-001, TC-003, TC-004) |
| C3 | Enabling the gate on an existing cluster adopts without rolling. | **Pass** (TC-002) |
| C4 | Rollout-relevant change rolls; management-side-only change refreshes without rolling (Policy A). | **Pass** (TC-005, TC-006) |
| C5 | Teardown cascades CR-owned objects; payload store freed; in-place core configs intact. | **Pass** (TC-007) |

## Verdict

**Pass** — all seven test cases passed and acceptance criteria C1–C5 are
validated. The fleet-safety guarantee holds: enabling the gate on a live
cluster adopts running NodePools without rolling a single Machine, and
management-side changes refresh served content without rolling. Gate-OFF
behavior remains the legacy ignition path.

Scope note: verification covered Replace-upgrade NodePools on AWS. InPlace
NodePool behavior under the new path was not exercised in this run and is a
follow-up.
